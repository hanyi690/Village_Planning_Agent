# ADR-002: Canonical Candidate Model

## Status
Proposed

## Context
Grounding and selection describe candidate parcels with two different models:

- `CandidateSite` — a typed Pydantic model in
  `backend/app/contracts/ground/grounding_contracts.py`. It is the
  output of the grounding hop: a spatial candidate with `site_id`, a list of
  `source_parcels` (BSMs), available geometry WKT, available area, hard
  constraint results, metrics, evidence refs, `target_ref`, and `project_ref`.
- `CandidateParcel` — a plain `@dataclass` in
  `backend/app/modules/select/selection.py`. It carries
  `bsm`, `geometry`, `dlmc`, `dlbm`, `area_ha`, `cluster`, `distance_m`, and
  `target_ref`.
- A historical bridge converted the two models:
  `candidate_site_to_parcels` (line 10) flattens each `CandidateSite` into
  one `CandidateParcel` per source BSM, and `grounding_to_candidate_parcels`
  (line 41) drives the whole conversion.

Two representations of the same domain concept force a bridge that must stay
in sync with both models and duplicates field semantics (area, target ref).
The canonical production boundary is now `modules/select/`; the old
`spatial/allocation/` implementation has been removed. Any remaining bridge
code must be treated as an edge adapter and must not recreate a second
selection service.

## Decision
`CandidateSite` is the canonical candidate model. It is owned by the grounding
module (`app/contracts/ground/grounding_contracts.py`) and generated by
the spatial grounding hop. It is consumed by selection and downstream
consumers.

`CandidateParcel` is a computation intermediate that is derived from
`CandidateSite`, not a canonical domain fact. The per-parcel flattening
(one `CandidateParcel` per source BSM, with computed `dlmc`, `dlbm`, and
`area_ha` converted from `area_sqm`) is a derived view produced at the edge of
selection, not stored as a source of truth.

The bridge in `select/adapter.py` is removed from the runtime path. Selection
consumes `CandidateSite` objects directly; the derived per-parcel shape is
built only where the geometric/parcel computation actually needs it.

| `site_id` | str | — | required |

| `available_geometry_wkt` | str | WKT | optional (default "") |
| `available_area_ha` | float | ha | optional (default 0.0) |
| `hard_constraint_result` | HardConstraintResult \| None | — | optional |
| `metrics` | dict | — | optional (default factory) |

| `target_ref` | str \| None | — | optional |
| `project_ref` | str \| None | — | optional |

| `target_ref` | str | — | optional (default "") |

## Classification
`CandidateSite` is a domain fact (an objective spatial grounding result).
`CandidateParcel` is a computation intermediate derived from it.

## Migration Boundary
The single entry point for old data conversion is the grounding output
boundary. A legacy grounding result that emits per-parcel dicts is normalized
into `CandidateSite` objects exactly once at the grounding hop. No runtime node
performs a site→parcel conversion in the middle of the pipeline.

## Consequences
What breaks:
- Consumers that import `CandidateParcel` from
  `app.modules.select.selection` no longer get the type; they must use
  `CandidateSite`.
- The `adapter.py` functions (`candidate_site_to_parcels`,
  `grounding_to_candidate_parcels`) are removed; callers must adapt.

What becomes easier:
- One canonical candidate model; no bridge to keep in sync.
- Selection and downstream consumers share a single typed shape.
- Derived per-parcel data is computed once at the edge, not redundantly.

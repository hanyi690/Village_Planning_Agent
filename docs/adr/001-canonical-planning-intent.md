# ADR-001: Canonical Planning Intent

## Status
Proposed

## Context
The planning intent generated by the PARSE hop exists in multiple representations:

- `SpatialPlanningIntent` — a typed Pydantic model defined in
  `backend/app/modules/schema/contracts/parse_contracts.py`. It is the
  canonical data contract shared between the PARSE Agent and downstream
  consumers (KG, EXECUTE tools). It contains zone targets, facility
  requirements, development axes, road targets, project targets, planning
  indicators, and the three-zones-three-lines structure.
- `_build_legacy_intent` — a one-off builder in
  `backend/app/agent/parse/compile_node.py:98` that converts a `PlanningProgram`
  (L3) into a `SpatialPlanningIntent` by hand-mapping each intervention
  category (`project`, `facility`, `road`, `restoration`, `protection`, `zone`)
  into the corresponding target collection. It is called from
  `compile_program_deterministic` (`compile_node.py:163`).

Having two construction paths for the same concept means a consumer can never
be sure which representation is authoritative, and any divergence between the
dict-style program and the typed contract must be reconciled in an ad-hoc
`backend/app/agent/select/adapter.py` bridge.

## Decision
`SpatialPlanningIntent` (in `app/modules/schema/contracts/parse_contracts.py`)
is the single canonical model for a parsed planning intent. It is owned by the
PARSE module and generated by the PARSE Agent (text-to-intent). Consumers are
KG and EXECUTE.

`_build_legacy_intent` is removed from the runtime path. No runtime node may
construct a `SpatialPlanningIntent` from a loose `PlanningProgram` dict. The
typed model is produced once by the PARSE Agent and propagated as the fact.

## Classification
Domain fact. The intent is a real-world parsed requirement, not a computation
intermediate or a render view. `SpatialPreference` / `AdjacencyRules` inside
`ZoneTarget` are also domain facts captured from the planning text.

## Migration Boundary
The single entry point for old data conversion is the checkpoint-import
boundary. When a legacy checkpoint carries a loose `PlanningProgram` dict, it
is parsed into a `SpatialPlanningIntent` exactly once at import time. No
runtime node performs the conversion.

## Consequences
What breaks:
- Any code path that still calls `_build_legacy_intent` no longer compiles;
  it must instead consume the typed `SpatialPlanningIntent` produced by PARSE.
- Consumers that relied on the loose dict shape must be updated to the typed
  contract fields.

What becomes easier:
- One authoritative representation for the intent; no dual source of truth.
- The `select/adapter.py` bridge no longer has to reconcile dict vs typed
  shapes.
- Type-checked access to intent fields across KG and EXECUTE.

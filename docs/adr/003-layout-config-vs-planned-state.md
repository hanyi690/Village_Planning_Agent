# ADR-003: Layout Config vs Planned State

## Status
Proposed

## Context
The result of planning is represented in two ways:

- `PlannedState` — a typed Pydantic contract in
  `backend/app/modules/schema/contracts/planned_state_contracts.py:56`. It
  holds the authoritative planned outcome: `parcels`, `zones`, `facilities`,
  `roads`, `axes`, `source`, and `provenance`. It is the canonical planned
  result consumed across the pipeline.
- `layout_configs` — a list of raw dicts (e.g. `{ "data": { "type":
  "FeatureCollection", "features": [...] } }`) that describe the same layers
  as GeoJSON FeatureCollections. It is read as a fact in business logic —
  notably `check_topology(layout_configs)` in
  `backend/app/agent/validate/checks.py:269`, which walks the raw dicts to
  validate geometries and detect gaps.

Having the planned outcome both as a typed `PlannedState` and as loose
`layout_configs` dicts means validation and other business logic read an
untyped render-oriented shape instead of the typed domain contract, and the
two can drift apart.

## Decision
`PlannedState` is the sole fact source for the planned outcome. It is owned by
the schema contracts module and generated by the EXECUTE/planning hop.

`layout_configs` is demoted to a render hint. It is a derived view used only
for rendering/export (map layers, GeoJSON output), never as a source of
authority. Business logic that currently reads `layout_configs` as a fact —
such as `check_topology` in `checks.py` — must read from `PlannedState`
instead. `layout_configs` may be regenerated from `PlannedState` at the render
boundary.

## Required Fields
`PlannedState`:
| Field | Type | Unit | Required |
|---|---|---|---|
| `version` | str | — | required (default "v1") |
| `parcels` | list[PlannedParcel] | — | optional (default factory) |
| `zones` | list[PlannedZone] | — | optional (default factory) |
| `facilities` | list[PlannedFacility] | — | optional (default factory) |
| `roads` | list[PlannedRoad] | — | optional (default factory) |
| `axes` | list[PlannedAxis] | — | optional (default factory) |
| `source` | str | — | optional (default "") |
| `provenance` | Provenance \| None | — | optional |

`layout_configs` (render hint, not authoritative):
| Field | Type | Unit | Required |
|---|---|---|---|
| per layer: `data.type` | str | — | render only |
| per layer: `data.features` | list | — | render only |

## Classification
`PlannedState` is a domain fact (the authoritative planned outcome).
`layout_configs` is a render view (GeoJSON presentation of the same facts).

## Migration Boundary
The single entry point for old data conversion is the render/export boundary.
A legacy planned outcome stored as `layout_configs` dicts is converted into a
typed `PlannedState` exactly once at import/load time. No business logic
converts `layout_configs` during validation or other runtime checks.

## Consequences
What breaks:
- `check_topology` and any other business-logic reads of `layout_configs` must
  be rewritten to read `PlannedState` geometry.
- Render code that still consumes `layout_configs` must generate it from
  `PlannedState` at the boundary.

What becomes easier:
- Validation reads the typed domain contract, not loose dicts.
- No drift between the typed planned outcome and the render layers.
- Geolayers are regenerated deterministically from the single fact source.

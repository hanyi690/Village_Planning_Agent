# 周报（2026-07-21 ~ 2026-07-25）

这周主要花在 Schema 和 Data 层的重新设计上，同时把下游几个模块（KG、PARSE、EXECUTE、parsing）的 README 全部重写或更新了一遍，让它们跟新的 schema 和系统设计对齐。中间穿插了删除旧 gis 模块和几次调研。整体方向是把数据模型从"以图层语义为中心"改到"以数据结构为中心"。

## Schema 层

旧版 30 多个空间要素类型全部直接继承 `SpatialFeature`，没有中间层。几何类型只靠一个运行时 property 判断，传错了也没人管，到下游空间运算才崩。另外，`GISDataBundle.landuse` 是个 `List[Any]`，加载数据时把现状和规划地块塞进同一个列表，遍历的时候同一块地出现两次。

新版在 `SpatialFeature` 和具体类型之间加了 `PointFeature`/`LineFeature`/`PolygonFeature` 三个中间基类，构造时就能校验几何类型。栅格另开了 `RasterDataset` 分支。地块拆成 `current_landuse` 和 `planned_landuse` 两个字段，不混装。

这个改动看起来只是加了几层继承，但实际影响到了 Data 层的智能推断——现在可以按几何形态先分桶，再在桶里做语义匹配，不用每个图层都手写注册。

后面又陆续补了几件事：把 `GISDataBundle` 从"一村一包"改成 `ProjectDataView`（项目级，多村+跨村图层+共享栅格）套 `VillageBundle`（村庄级）；新增 `TableDataset` 类型，把人口结构、管制规则这些非空间表格从"文档"里拆出来；把设施和注记分开（设施是空间实体，注记是表达要素，老代码里 `CurrentFacility` 居然是从注记图层派生出来的）；三区三线补了 `BaseControlZone` 管控抽象和 `ThreeZoneItem`。

中间借助了 21 份专业教材和规范文档，发现 `PlannedLandUseParcel` 对照 QMDLTB 规范缺了 10 个字段、`CurrentLandUseParcel.sddlbm` 应该用国标编码但实际用了附录5、设施类型太粗（GB50445 要求 6 类整治设施，我只做了 1 个 `BaseFacility`）、防灾减灾基本是空白。这些补到了 v4.3 的设计里。

## Data 层

旧版的问题是两个极端：要么每个图层都要在注册表里手写一行（28 个 layer_type 硬编码），要么未注册的直接丢弃。现在改成双轨——已注册的走严格校验，没注册的走智能推断：先看几何类型分桶，再拿字段名去知识库里匹配，然后抽样编码值去字典里查，最后动态生成模型。栅格和表格也各有一套推断流程。

另外把项目配置和数据源配置拆开了：`sources.yaml` 管物理连接（端点、凭据、CRS），`projects.yaml` 管项目逻辑（哪些村参与、每村覆盖哪些数据源、用户上传了啥）。之前全塞在一个文件里，每次加项目都得改 sources 配置。

## KG 层

KG 的设计文档重写了，两个主要变化：一是 KG 从村庄级上移到项目级（数据视图上移了，KG 不跟会产生断层）；二是加了 `ConstraintCompiler` 的设计——KG 存的是语义约束，MIP 要的是数值矩阵，中间需要一个编译器把两者桥接起来，不能直接让 MIP 去查 SPARQL。

旧 README 里标了 5 个差距（还在读 raw dict、PARSE 结果没入 KG、反向依赖 tools 层、查询模板 12/28 未用），加上新架构需要的项目级改造和 ConstraintCompiler，一共规划了 K1-K5 五个任务，排在 OPTIMIZATION_TASKS 的批次 5-6。

## PARSE / EXECUTE / parsing 模块

parsing 模块之前没有 README，这周新建了。它定位是"文本提取工具层"，跟 PARSE Agent 的关系是手和脑——parsing 做确定性提取（markdown 表格、regex 约束、分节分类）和 LLM 结构化提取，PARSE 做编排和格式化。产出的是中间 Pydantic schema，最终由 PARSE 的 format 节点转成 `parse_contracts` 的契约类型。

PARSE 和 EXECUTE 的 README 更新了，主要是把过时的引用修掉（`gis/spatial_context.py` 改成 `spatial_ops/context.py`），加上跟 `ProjectDataView` 和 `ProjectKG` 的对接说明。PARSE 从 `ProjectDataView` 取 `SpatialContext`（现在支持多村），产出写入 `ProjectKG` Layer 3。EXECUTE 从 `ProjectDataView`（`VillageBundle`）读类型化地块，经 `ConstraintCompiler` 从 `ProjectKG` 取 MIP 约束，产出写回 `village.planned_landuse` 和 `project.tables`。

这三个模块的代码大修（PARSE 拆子包、KG 类型化摄入、EXECUTE 接入真实工具）排在 OPTIMIZATION_TASKS 的批次 5-8，设计文档先行。

## 调研

做了两次调研。一次用 Exa 查了 305 个来源，确认"图层=容器+要素类型化"是主流 GIS 软件（QGIS、ArcGIS、PostGIS）的通用模式，以及现状/规划分离是国标强制要求（209001/209002）。另一次读了项目里 21 份教材和规范文档，对照当前 schema 找覆盖缺口，结果写在了 `docs/gis/diagnostics/SCHEMA_COVERAGE_AUDIT_2026-07-25.md` 里。

## 实际跑通的结果

本周在改设计的同时，layout pipeline 实际跑了两轮（7-23 和 7-24），金田村从头到尾跑通了"加载数据 -> 构建 KG -> MIP 分配 -> 生成图层 -> 渲染出图"的完整链路。两轮都有实际的验证数据，也在 optimizer 上做了一些改进。

**7-23 跑的结果**：KG 构建了 9,395 个三元组，660 个邻接关系，1 条约束。MIP 求解器跑了 5,280 个二元变量，最优解目标值 17,244。产出了 11 个 GeoJSON 图层（function_zone、planning_zone、infrastructure、space_control_zone、land_use_zone、boundary、current_landuse、current_road、farmland_protection、ecological_protection、land_balance），3 张渲染图（planning_zone.png、comparison.png、composite.png）。总共跑了 63 秒，其中分配 5.4s、KG 构建 8.2s、渲染 11.1s。

**7-24 改进后的结果**：KG 三元组从 9,395 涨到 12,459（+33%），约束从 1 条涨到 4 条。新增了 `facility_point.geojson` 图层（设施点从注记图层里拆出来了）。总时间从 63s 降到 35.6s（-43%），其中分配从 5.4s 降到 2.7s（-50%）、KG 构建从 8.2s 降到 6.1s（-26%）、渲染从 11.1s 降到 2.9s（-74%）。Validation 从 8 项检查扩展到 9 项（新增了 VNE 合规检查），约束调整也增加了建设用地上限和生态保护下限的检查。

**PARSE 方面**：跑了一次解析，pipeline_trace 有 64KB 的详细 trace，但报告生成因为 `SpatialPlanningIntent` 类型化后报告生成器还在用老的 dict 方式访问，崩了。这是下周要修的点——报告生成器要适配 Pydantic 类型。

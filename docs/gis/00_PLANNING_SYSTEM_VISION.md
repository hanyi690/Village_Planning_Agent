## 0. 初期目标 vs 终极目标

### 0.1 初期目标（Plan-then-Execute，当前可推进）

**输入**：村庄规划报告文本 + 现状 GIS 数据（矢量，660 地块）
**输出**：整村规划图（分区着色 + 设施点 + 轴线 + 图层），可解释的 GDB 汇交成果
**路径**：PARSE（意图提取）-> MIP allocate（批量分区）-> generate（程序化合成）-> export -> render
**范式**：Plan-then-Execute（LLM 做规划，优化引擎做执行）——2025-2026 年 6/6 论文确认的 SOTA

**这对应的是"整村生成 / 批量重分类"场景**——从规划文本直接生成整村的空间布局图。
PARSE Agent 已实现（v11, Think-Then-Format），MIP allocate + generate 已实现。
初期需修补的是**质量项**（GHYTBM 格式校验 / area_ratio 语义 / SpatialAnchor 注入），
**非架构性缺口**。

### 0.2 终极目标（闭环 ANALYZE/PLAN/DELIVER）

**额外能力**：栅格分析（DEM/双评价/适宜性）、文本<->空间闭环迭代、原子操作落地
具体项目、管制规则生成、条款级溯源、5 目录汇交结构。

**初期目标 == 终极目标的 PLAN 阶段地基**。所有初期建设都是终极闭环的组成部分，
不浪费。

### 0.3 为什么原文档偏了

原 `docs/gis/` 把"操作执行引擎/绘图员"（Phase 2.5，未实现）当作系统全貌，而实际
代码路径是 `PARSE -> MIP allocate -> generate`（Plan-then-Execute）。

终极目标是**智能化乡村规划系统**：文本规划过程中 GIS 工具随时可用、提供栅格与矢量分析
支撑决策；文本规划也可直接操作 schema 中的专业数据（栅格 + 矢量）；文本与空间双向迭代、
闭环收敛；最终产出完整、可解释、可汇交的规划成果。

## 1. 终极目标

输入一个村庄的**现状资料**（三调数据、三区三线、DEM/DOM、上位规划、村民需求），
系统像规划师一样完成：

| 人类规划师做什么               | 系统对应能力                                     | 当前状态            |
| ------------------------------ | ------------------------------------------------ | ------------------- |
| 现状调查、形成工作底图         | 摄入多源数据（矢量 + 栅格），归一化到 CGCS2000   | ⚠️ 矢量齐，栅格缺 |
| 双评价 / 地形 / 适宜性分析     | 栅格分析（坡度/坡向/汇水）+ 矢量叠加（双评价）   | 🔴 缺失             |
| 编制规划文本与图件（来回切换） | 文本 ↔ 空间闭环迭代，GIS 工具随时调用           | ❌ 单向             |
| 落实项目、划线、分区           | 操作执行（create/split/merge/modify/reclassify） | ❌ 设计中           |
| 产出"一图一表一规则 + 数据库"  | 可解释汇交成果 + 全程溯源                        | ⚠️ 部分           |

**一句话定义**：

> 给定村庄现状资料，系统产出**可解释、可汇交**的村庄规划成果包（一图一表一规则 + 数据库），
> 过程中文本规划与空间分析双向闭环，每一条规划条款、每一个图斑变更都能溯源到上位依据或
> 规划师决策。

## 2. 人类规划工作流 -> 系统三阶段能力模型

依据 `reference/HUMAN_PLANNING_WORKFLOW.md`（提炼自《广东省村庄规划编制基本技术指南》
及专业教材），人类规划工作流分四阶段：**现状调查 -> 规划编制 -> 规划报批 -> 规划公告**。
其中"报批/公告"属行政流程，系统不覆盖；"调查 + 编制"是系统的核心，映射为三阶段能力模型：

```
人类工作流                        系统能力模型
─────────────────────────────────────────────────────────────
现状调查                          ┌── ANALYZE（现状调查 + 分析）──┐
  三调/三线/DLG/DOM -> 工作底图   │  摄入：矢量(三调/三线/现状)    │
  地形/双评价/适宜性分析          │        + 栅格(DEM/DOM)         │
                                  │  分析：地形/双评价/适宜性/     │  ← 当前 🔴
                                  │        可达性/覆盖/承载力      │
                                  │  产出：工作底图 + 评价图 +     │
                                  │        SpatialContext(富化)    │
                                  └──────────────┬────────────────┘
                                                 ↓ 喂入
规划编制                          ┌── PLAN（规划编制，闭环）────────┐
  规划文本 <-> 图件 来回切换      │  文本 ↔ 空间 双向迭代           │  ← 当前 ❌ 单向
  落实指标、划线、分区、布项目    │  规划文本/管制规则 ↔ 用地布局/  │
                                  │                控制线/项目       │
                                  │  GIS 工具随时可调用做分析支撑   │
                                  │  操作执行引擎落地变更           │
                                  └──────────────┬────────────────┘
                                                 ↓ 产出
规划成果                          ┌── DELIVER（汇交成果，可解释）──┐
  一图一表一规则 + 数据库         │  一图：村庄规划总图(14层组装)   │
                                  │  一表：近期建设项目表(11列)     │
                                  │  一规则：管制规则(6大类)        │  ← 当前 1/3 deprioritized
                                  │  一库：规划数据库(4必选图层)    │
                                  │  可解释：changelog + 条款溯源   │
                                  └────────────────────────────────┘
```

**三阶段不是串行瀑布，而是闭环**：PLAN 阶段可随时回调 ANALYZE 的分析工具（"这块地坡度
多少？能否建设？"），DELIVER 的校验不通过也会回灌 PLAN 修订。这是与原"单向流水线"的根本
区别。

## 3. 核心设计原则

### 3.1 文本与空间闭环（Text ↔ Spatial Closed Loop）

规划文本（发展目标/管制规则/建设项目表/村民决议）与空间数据（用地布局/控制线/图斑属性）
是同一规划的两个表征，必须**双向迭代、闭环收敛**：

- **文本 -> 空间**：规划条款落地为图斑变更（"允许建设区内不得安排基本农田" -> 约束注入；
  "新建 400㎡展销中心" -> create 操作）。
- **空间 -> 文本**：空间分析结果回灌文本（"经地形分析，X 地块坡度 >25°，建议由建设区
  调整为禁建区，相应修订管制规则"）。
- **闭环收敛**：文本修订触发空间重算，空间校验不通过触发文本修订，直至一致。

> **实现差距**：当前 `gis_agent` 是 Router Agent 的终端叶节点，跑完即返回，不回灌文本
> 规划。闭环需要把 GIS 分析/查询工具提升为 PLAN 阶段可随时调用的工具，并在 state 中
> 维护"待落地的文本变更"与"待解释的空间变更"双向队列。

### 3.2 分析驱动规划（Analysis-Driven Planning）

人类规划师划定三区三线、布局产业用地的依据是**双评价 + 地形分析 + 现状研判**，不是凭空
绘制。系统必须让 LLM 在规划决策时能调用栅格与矢量分析工具：

| 分析类型   | 输入          | 输出                    | 规划决策影响            |
| ---------- | ------------- | ----------------------- | ----------------------- |
| 地形分析   | DEM(栅格)     | 坡度/坡向/起伏度        | >25°禁建，南坡优先居住 |
| 双评价     | 栅格+矢量     | 生态/农业/城镇适宜性    | 三区三线划定依据        |
| 建设适宜性 | DEM+土壤+水文 | 适宜/较适宜/一般/不适宜 | 建设边界划定            |
| 洪涝风险   | DEM+水系      | 淹没范围(10/20/50年)    | 禁建区/安全控制线       |
| 可达性     | 道路(矢量)    | 等时圈/设施覆盖         | 公服设施选址            |
| 承载力     | 资源+环境     | 承载等级                | 建设规模上限            |

> **实现差距**：DEM/DOM 摄入 🔴、地形分析 🔴、双评价 🔴、适宜性 🔴。可达性/覆盖分析
> 工具已存在（`tools/gis_data/analytics.py`）但不在规划推理回路中。栅格数据是当前最大
> 的能力缺口--`GISDataBundle.dem` 字段已预留但从未填充。

### 3.3 可解释汇交成果（Explainable Deliverable）

成果不是"14 个 GeoJSON 文件"，而是**符合广东省汇交标准的可解释成果包**，每一项都能溯源：

- **一图**：村庄规划总图（5 条控制线 + 用地布局 + 附表 1 + 附表 2，比例尺 ≥1:2000）。
  由 14 层 GeoJSON 组装渲染。
- **一表**：近期建设项目表（11 列：项目类型/名称/空间位置/用地面积/建筑面积/资金规模/
  筹措方式/责任主体/协作部门/建设方式/备注）。
- **一规则**：村庄规划管制规则（6 大类：生态保护/耕地和永久基本农田保护/历史文化/
  建设空间管制/安全防灾/其他），以村规民约表述。
- **一库**：规划数据库（4 必选图层 GHCFW/QMDLTB/TDYT/JSYDGZQ，CGCS2000，.mdb）。
- **可解释**：`changelog.jsonl` 记录每一次图斑变更的来源文本/前快照/后快照/合规检查/
  确认人；每条管制规则可溯源到上位依据或本级决策。

> **实现差距**：14 层 GeoJSON + 2 表已具备；**管制规则生成被降级为 P2**，需提升为核心；
> .mdb 输出、5 目录汇交结构、条款级溯源待补。

### 3.4 Agent 是规划助手，不是规划师

延续人机协同底线（见 `01_DESIGN_GOALS.md §9`）：Agent 负责分析、起草、落地、校验，
**不做规划决策**。不确定性必须由人消除：文本未指定用途时反问，空间定位有歧义时列候选，
分析结论有多种解读时呈现依据让人定。"绘图员"是 Agent 在 PLAN 阶段落地操作时的角色之一，
不是 Agent 的全部身份。

```

└──────────┬──────────────────────────────────────┬───────────────────┘
           │                                      │
   ┌───────▼────────┐                   ┌────────▼─────────┐
   │  ANALYZE 工具集 │                   │  PLAN 落地引擎    │
   │  (栅格+矢量分析) │  ← 当前 🔴 缺失   │  (操作执行)       │  ← 当前 ❌ 设计中
   │  - terrain      │                   │  - 5 原子操作     │
   │  - suitability  │                   │  - 合规预检       │
   │  - dual_eval    │                   │  - 人工确认       │
   │  - accessibility│                   │  - MIP 辅助(批量) │
   │  - coverage     │                   │  - changelog      │
   └───────┬────────┘                   └────────┬─────────┘
           │ 分析结果回灌 state                    │ 变更落地
           └──────────────┬───────────────────────┘
                          ↓
          ┌───────────────▼────────────────┐
          │       DELIVER 成果组装          │
          │  一图(总图) + 一表(项目表)      │
          │  + 一规则(管制规则) + 一库(mdb) │
          │  + changelog 溯源               │
          └────────────────────────────────┘
```

**与现架构的关系**：

- ANALYZE 工具集是**新增**能力（栅格摄入 + 分析工具），对应 `tools/gis_data/` 扩展 +
  新建 `tools/gis_analyze/`（terrain/suitability/dual_eval）。
- PLAN 落地引擎即 `01_DESIGN_GOALS §3.4` 的操作执行引擎（Phase 2.5），从"系统全貌"
  降格为"PLAN 阶段的落地机制"。
- DELIVER 是 `02_OUTPUT_ARCHITECTURE` 的重组：以"一图一表一规则 + 一库"为组织原则，
  14 层 GeoJSON 是"一图"与"一库"的数据底座。
- 闭环的关键改造点在 Router Agent：把 `gis_agent` 从终端叶节点改为"可回访的工具集"，
  state 增加"文本待落地队列"与"空间待解释队列"。

## 5. 闭环交互范式

闭环不是把现有单向流水线跑两遍，而是**规划主控与工具集的多轮对话**：

```
Router: "产业用地布局在哪里合适？"
  -> 调 analyze_suitability(产业, DEM+土壤+交通)
  <- "X 地块适宜度高（坡度 8°、邻近主干道、非基本农田）"
Router: "好，在该地块安排 400㎡ 经营性建设用地，写入建设项目表"
  -> 调 edit_parcel(create, X, 400, 经营性建设用地)
  -> 合规预检通过 -> 人工确认 -> 落地 + changelog
  <- "已落地，BSM=X-001，GHYTBM=2124"
Router: "相应地，管制规则需补充：经营性建设用地建筑密度 ≤40%、高度 ≤10m"
  -> 调 update_control_rule(建设空间管制, 产业发展空间, ...)
  <- "管制规则条款 R-04 已更新，溯源到本项目"
Router: "校验整体成果"
  -> 调 validate_layout(8项检查 + 8条硬约束)
  <- "通过"
Router: "组装汇交成果"
  -> 调 deliver(一图一表一规则 + 一库 + changelog)
```

每一步都有工具调用、有结果回灌、有人工确认点。文本与空间始终同步演进。

| 人机协同底线            | 保持                                 | 不变           |

## 8. 验收标准

系统达成终极目标的标志，是能对任意一个测试村庄产出**通过广东省汇交质量检查**的成果包：

1. **完整性**：5 目录齐全（规划文本/图件/表格/数据库/批文），4 必选图层非空。
2. **合规性**：8 条硬约束全通过（不调整基本农田/禁建区、建设用地规模不增等）。
3. **可解释性**：随机抽 10 个图斑变更，都能在 changelog 找到来源文本与前快照；随机抽 5 条
   管制规则，都能溯源到上位依据或本级决策。
4. **闭环性**：规划过程中至少出现一次"空间分析结果回灌文本修订"的闭环轨迹。
5. **分析支撑**：三区三线划定有双评价/适宜性分析结果作为依据，非凭空生成。

当前系统距此标准的主要差距：ANALYZE 缺失（验收 5 不达标）、闭环缺失（验收 4 不达标）、
管制规则缺失（验收 1/3 不达标）。

## 2. 发现 1：原子操作（create/split/merge）并非成熟范式

**结论：零命中。** 所有检索到的论文都是关于空间**查询**（NL2SQL），而非空间**编辑**。
没有任何已发表系统描述过 LLM 输出离散的 create/split/merge 操作对 GIS 图层执行。
这意味着我们的原子操作设计是**新颖的**——风险更高，但差异化也更大。

**设计影响**：原子操作应作为我们系统的**差异化能力**，而非行业标准。初期目标应优先
使用已验证的 Plan-then-Execute 范式（MIP allocate + generate），原子操作作为增量
编辑能力保留。

## 3. 发现 2：主导范式是"Plan-then-Execute"（意图 -> 优化）

6 个已发表系统均采用相同的模式：LLM 从文本中提取结构化意图，优化引擎执行空间布局。

| 系统                      | 会议/年份       | 范式                                                                                                    | 引用                                                   |
| ------------------------- | --------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| **UrbanXplain**     | SIGSPATIAL 2025 | 文本 -> LLM 分区命令 -> 结构化建筑规格 -> 3D 渲染。**可解释推理**和**可追溯性**是核心功能。 | [DOI](https://doi.org/10.1145/3748636.3762792)          |
| **Text-to-3D City** | CAVW 2026       | "Plan-then-Execute"：LLM 规划器将文本转换为结构化城市计划 -> PCG 执行器执行。                           | [DOI](https://doi.org/10.1002/cav.70124)                |
| **Co-Layout**       | AAAI 2026       | LLM 提取约束 -> 基于网格的整数规划优化。粗到细策略。                                                    | [DOI](https://doi.org/10.1609/aaai.v40i17.38452)        |
| **Intelli-Planner** | WWW 2026        | LLM + DRL：LLM 制定目标，强化学习优化，多利益相关方评分。                                               | [DOI](https://doi.org/10.1145/3774904.3793019)          |
| **Lang2Plan**       | 2026            | 多代理：NLP -> 规划 -> 布局 -> 验证 -> 渲染。反馈循环。                                                 | [DOI](https://doi.org/10.1145/3774905.3793111)          |
| **Prompt-to-Plan**  | ICNWC 2026      | 多代理管线：NLP 预处理 -> 规划 -> 布局生成 -> 验证 -> 渲染。                                            | [DOI](https://doi.org/10.1109/icnwc68145.2026.11518170) |

**设计影响**：我们的 PARSE（意图提取）+ MIP allocate（优化）+ generate（程序化合成）
设计**完全符合** 2025-2026 年的 SOTA。不需要范式转换。UrbanXplain 对"可解释推理"
和"可追溯性"的强调与我们对可解释汇交成果的目标一致。

## 4. 发现 3：空间锚定 — LLM 在推理上优于事实性知识

**"Coordinates from Context: Using LLMs to Ground Complex Location References"**
(Masis & O'Connor, UMass Amherst, EACL 2026)

| 发现       | 详情                                                     |
| ---------- | -------------------------------------------------------- |
| LLM 的弱点 | 在生成准确的地理事实性知识（中心坐标）方面表现不佳       |
| LLM 的优势 | 在给定事实性知识的情况下进行空间推理方面表现良好         |
| 混合方法   | 传统 gazetteer 提供候选坐标，LLM 在候选坐标上推理        |
| 效率       | 经过微调的小型 LLM 可以达到与大型模型相当的性能          |
| 表示       | 使用 bounding box 链接位置，提供简单且信息丰富的定位方式 |

**设计影响**：验证了我们当前的 Gazetteer + LLM 空间锚定策略。实施路径：

- Gazetteer 层（确定性）：天地图 + villages-ML -> 候选 VillageGroup + 地块
- LLM 推理层（语义）：给定候选 + 约束，对最佳目标地块进行排名
- 与 EACL 2026 的混合方法一致

## 5. 对系统设计决策的总结

| 决策                           | 结论                                                     | 外部验证                         |
| ------------------------------ | -------------------------------------------------------- | -------------------------------- |
| PARSE + MIP allocate 范式      | 坚守。Plan-then-Execute 是 SOTA。                        | 6/6 论文确认                     |
| 原子操作（create/split/merge） | 新颖，非标准。初期用于`create`（项目落地），其余预留。 | 无先例，属差异化                 |
| 空间锚定（Gazetteer + LLM）    | 坚守。混合方法是正确的。                                 | EACL 2026 确认                   |
| 可解释性/可追溯性              | 坚守。UrbanXplain 将其列为关键特征。                     | SIGSPATIAL 2025 确认             |
| 验证反馈循环                   | 考虑添加。Prompt-to-Plan 使用验证代理进行反馈。          | 我们已有 VALIDATE Evaluator Gate |

# 项目周报：从报告生成器到结构化规划分析系统

**汇报周期：** 2026 年 8 月 25 日—8 月 29 日
**项目：** Village Planning Agent
**汇报对象：** 指导老师
**本周主题：** L1/L2/L3 规划链路结构化升级、证据与空间认知边界收敛

## 一、本周工作结论

本周工作的核心，不只是给原有报告生成器增加几个结构化字段，而是围绕“规划系统如何从原始资料形成可解释、可验证、可落地的规划结果”重新收敛系统架构。

更准确的概括是：项目正在从“输入资料—调用模型—生成报告”的报告生成式流水线，升级为“资料理解—证据组织—分层分析—规划意图—空间接地—方案选择—执行交付”的结构化规划分析系统。

其中，L1、L2、L3 的角色正在发生变化：

- **L1 不再只是报告内容抽取器**，而是把原始资料整理为带来源、类型、范围、置信度和状态的结构化事实。
- **L2 不再只是生成一段分析文字**，而是围绕问题、目标、需求、适宜性和策略形成可验证的规划认知结果。
- **L3 不再只是编写规划报告或方案描述**，而是把 L2 的分析结果编译为带语义、约束、证据 lineage 和后续接地要求的规划意图。

因此，本周可向老师汇报为：**完成了 L1/L2/L3 从报告生成阶段向结构化分析阶段迁移的核心架构收敛，并同步补齐了证据、空间认知和工作流边界。**

## 二、与历史周报的衔接：老师已经知道什么

本周报不能把项目重新讲成“刚开始做一个规划报告系统”。从 8 月 23 日和 8 月 24 日周报可以判断，老师此前已经了解并接受了以下项目认知：

1. **项目已经有过真实运行闭环。** 历史周报曾汇报过 `ScenarioSet → ApprovedExecutionInput → EXECUTE → VALIDATE → RECONCILE → DELIVER` 的真实窄切片闭环，前端也能显示规划图层。因此，本周不应说“我们刚刚实现了从分析到交付”，而应说“我们在已有窄切片闭环的基础上，继续重构其上游事实、证据和规划认知”。
2. **当前成果不是全村法定规划。** 历史周报反复强调单地块或同源地块窄切片已验证，但 coverage、道路网络、拓扑分区和多类 worker 混合执行仍是 GAP/PARTIAL。本周应继续保持这个边界，避免把结构化重构误报为全村规划已经完成。
3. **空间接地和执行边界是老师已经关注的重点。** 之前已经说明 `fully_available`、`partially_available`、`fully_unavailable`、`unknown` 的区别，也说明邻地不能因为相邻就自动进入执行。因此，本周可以把这些内容作为“既有边界继续被迁移到新模块”的延续，而不必从概念定义开始展开。
4. **可审计性比报告文字更重要。** 历史周报已经使用 source BSM、footprint、remainder、candidate geometry、ValidationCertificate、DeliveryGate 等对象说明系统行为。由此可以判断，老师关心的已经不是页面上有没有一份完整文字，而是每个规划结论能否追溯到事实、证据、空间对象和执行结果。
5. **之前的工作重点是把执行闭环做实，本周转向上游认知重构。** 8 月 24 日周报的中心是“共享地块执行边界与真实闭环”，本周的重点则前移到了 DATA、Evidence、L1、L2、L3、Context Runtime 和模块契约。这是工作重心的自然推进，而不是另起炉灶。

因此，向老师汇报时建议采用“承接—提升”的叙事：**前期已经证明窄切片可以落到真实空间并完成交付；本周进一步把这条链路前面的事实构建、证据组织和规划认知结构化，使系统从一个能够完成局部交付的报告/规划原型，逐步升级为可解释、可验证、可扩展的规划分析系统。**

历史周报还留下了一个需要主动说明的认知风险：之前的 `delivery_status=complete` 只表示特定 scoped run 的交付闭合，并不代表全村规划完成。本周即使新增了更多模块和设计文档，也不能用“模块数量增加”替代真实运行证据。后续汇报应继续区分“代码和契约已建立”“选定切片已通过测试”“完整真实会话已验证”三个层次。

## 四、系统模块简述

当前系统可以用下面这条主链理解：

```text
原始资料 / GIS / 外部 provider
              ↓
DATA 与 Source Cognition
              ↓
Evidence / KG / Context Runtime
              ↓
L1 结构化事实
              ↓
L2 规划认知
              ↓
L3 规划意图与 Planning Program
              ↓
Target Projection / GROUND
              ↓
SELECT / EXECUTE
              ↓
DELIVER：报告、地图、方案和诊断信息
```

### 1. DATA 与 Source Cognition：资料入口和来源理解

这一层负责接收报告、表格、GIS、地图服务和其他外部资料，并识别资料中的表格结构、字段含义、来源、空间范围和可用性。它的目标不是简单读取文件，而是为后续分析建立统一的 source identity 和数据边界。

本周新增或强化了外部观察缓存、provider registry 和采集验证脚本，为后续把多来源数据纳入统一证据体系做准备。

### 2. Evidence / KG：证据组织和知识关联

Evidence 层负责检索和组合证据，Knowledge Graph（KG）负责维护实体、地点、设施、关系和来源之间的关联。它们共同回答：某个事实来自哪里、涉及哪个空间对象、有哪些相互支持或冲突的来源、当前证据是否足够。

这一层是 L1/L2/L3 的事实基础，也是系统避免“模型自行补全不存在信息”的重要边界。

### 3. Context Runtime：给模型提供受控上下文

Context Runtime 负责根据当前阶段、维度、证据和 token 预算，生成模型可以使用的上下文。它把“所有资料都塞给模型”改成“按照阶段和权限提供必要信息”，同时保留来源和诊断信息。

这使得 L1、L2、L3 的模型调用不再是无边界的文本生成，而是受到上下文、证据和契约约束的结构化分析。

### 4. L1：结构化事实构建

L1 的任务是从资料和证据中构建规划事实，例如人口、设施、土地、交通、生态约束、空间实体和空间关系等。每个事实应尽量携带：

- fact type；
- 来源引用和原文片段；
- 空间范围或空间 mention；
- 置信度与状态；
- 相关观察或约束引用；
- 是否需要继续检索。

所以 L1 的产物不应理解为“报告摘要”，而应理解为后续规划推理可以复用的事实底座。

### 5. L2：规划认知与问题分析

L2 负责把 L1 事实转化为规划问题、目标、需求、适宜性判断和策略方向。例如，系统需要判断某个问题是什么、影响哪些对象、产生了哪些需求、哪些约束是硬约束、哪些策略具备可行性。

L2 的重点是形成结构化、可检查的分析结果，而不是直接写最终报告。它需要能够表达证据不足、结论不确定、冲突未解决等状态。

### 6. L3：规划意图与方案语义编译

L3 负责把 L2 的认知结果编译为规划意图，例如规划目标、空间目标、设施目标、关系要求、约束条件和执行前的 claim。L3 输出的是后续空间投影和方案执行可以消费的 Planning Program 或等价结构，而不是最终展示文本。

L3 还需要保留从 claim 到 L2 分析、L1 事实和原始证据的 lineage，确保后续能够解释“为什么提出这个规划目标”。

### 7. Target Projection / GROUND：把意图落到空间

这一层把 L3 的抽象规划意图投影为候选目标、空间引用、候选几何和约束关系，并通过 GROUND 过程检索、解析和验证真实空间对象。

如果目标无法解析、空间范围不明确或证据不足，系统应保留诊断状态并要求补充证据，而不是把模糊文字直接当作可执行空间。

### 8. SELECT / EXECUTE / DELIVER：选择、执行和交付

SELECT 负责从候选方案中进行选择和审批；EXECUTE 负责把批准的方案转成具体的规划执行对象、地块变化、道路或设施安排；DELIVER 负责输出报告、地图、方案代码树和过程诊断。

因此，报告只是最终交付物之一。系统真正的核心产物是可追溯的事实、分析、意图、空间对象和执行状态。

## 五、本周完成情况

### 已完成或基本完成

1. **结构化契约体系进一步收敛。** L1/L2/L3、Evidence、Ground、Workflow、Delivery 等领域的契约被拆分并明确职责。
2. **L1/L2/L3 的阶段产物从文本导向结构化对象。** 事实、规划认知和规划意图均有更明确的数据结构、状态和验证入口。
3. **证据 lineage 和空间范围表达得到强化。** 事实不再只保留结论，而是逐步绑定来源、空间 mention、feature identity 和检索状态。
4. **上下文和结构化 LLM 运行时得到重构。** 模型输入受到阶段边界、证据边界和结构化输出规则约束。
5. **工作流目录和门禁边界完成一轮重组。** workflow、routing、gates、delivery、recovery 等职责更加清晰。
6. **多来源外部证据能力开始形成。** 增加 provider registry、外部观察缓存、地图检索器、采集脚本和验证脚本。
7. **设计文档完成重新分层。** 已区分目标设计、当前运行时、迁移台账、ADR、历史材料和审计证据，减少不同文档之间的语义冲突。

### 尚未能宣称完全完成的部分

需要特别说明：当前设计文档中的“目标系统”不等同于所有能力都已经在真实运行中完成。`docs/architecture/CURRENT_RUNTIME.md` 和 `docs/design/05_MIGRATION.md` 仍然标记了部分 `PARTIAL` / `GAP` 边界。

目前更准确的状态是：**结构化架构和模块边界已经建立并持续收敛，但跨阶段真实运行、外部数据稳定性、完整空间接地和 SELECT/EXECUTE 的全链路验收仍需要继续验证。**

## 六、对本周工作的学术/工程意义概括

本周工作的主要价值，是把系统的研究问题从“如何让模型生成更完整的村庄规划报告”，推进到：

> 如何构建一个能够从多源资料中形成结构化事实，基于证据进行分层规划推理，并将规划意图可靠映射到真实空间和可执行方案的规划智能系统。

这意味着项目的技术重点已经从单纯的 prompt 和报告格式，转向以下更具研究价值的问题：

- 多源异构资料如何形成统一的证据和实体认知；
- L1/L2/L3 如何通过显式契约实现可组合的规划推理；
- 不确定性、证据缺口和空间歧义如何在流程中被保留和传递；
- 规划语言如何投影为可验证的空间目标和执行对象；
- 如何通过测试、lineage 和诊断信息评估系统是否真正完成规划，而不是只生成了文字。

## 七、下周工作方向

### 方向一：完成 L1/L2/L3 的真实运行闭合

继续围绕一个稳定的村庄规划样例，验证：

1. L1 是否能从真实资料稳定生成可追溯事实；
2. L2 是否能基于事实形成结构化问题、目标和策略；
3. L3 是否能生成带 lineage、空间要求和约束的规划意图；
4. 任一阶段出现证据不足时，是否能正确进入 diagnostic、deferred 或 HUMAN 状态。

### 方向二：打通 Evidence → GROUND → SELECT 的闭环

重点验证外部地图证据、内部 GIS、实体解析、候选几何和空间约束之间是否能够稳定衔接，减少“事实有了但无法落地”的断点。

### 方向三：用可重复验收代替单次演示

完善 acceptance probes、recorded replay、结构化契约测试和最小真实运行样例，形成可重复的验收材料。后续向老师展示时，应尽量展示：输入、结构化事实、证据引用、规划意图、空间候选、诊断和最终交付之间的完整链路。

### 方向四：整理迁移与旧路径退出计划

当前仓库仍处于新旧路径并存后的收敛阶段。下一步需要依据 `05_MIGRATION.md` 明确：

- 哪些旧报告生成路径已经可以删除；
- 哪些兼容适配仍需保留；
- 哪些模块需要迁移到新的 contracts/modules/runtime 目录；
- 每个旧路径的退出条件和回滚方式是什么。

### 方向五：形成论文或阶段成果的评价指标

建议逐步建立以下指标：

- 结构化输出合法率；
- 事实来源覆盖率；
- 证据充分率和缺口闭合率；
- 空间实体解析成功率；
- L1→L2→L3 lineage 完整率；
- 规划意图到可执行空间对象的投影成功率；
- 失败时诊断和人工介入是否准确。

## 八、建议向老师口头汇报的简短版本

本周我们主要完成了规划系统的一次架构升级。原来的系统更像是从资料直接生成规划报告，现在开始拆成 DATA、Evidence、L1、L2、L3、GROUND、SELECT、EXECUTE 和 DELIVER 等结构化模块。L1 负责把资料变成带来源和空间范围的事实，L2 负责形成问题、目标、需求和策略，L3 负责把这些分析结果编译成带约束和 lineage 的规划意图，之后再通过空间接地和方案选择形成可执行结果。与此同时，我们重构了上下文和结构化 LLM 运行时，增加了外部地图证据缓存、provider 验证和审计文档。下一步不是继续单纯优化报告文字，而是用真实样例把 L1 到 L3 再到空间执行的全链路跑通，并建立可重复的验收指标。
